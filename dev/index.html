Compiler pipeline

Everything the compiler does to a program passes through the same frontend: lex → parse → check → analyze. Then a program takes one of two roads: the interpreter evaluates it directly (CPS, effects first-class), or the wasm backend compiles it to a WasmGC module with the same observable behaviour.

Frontend (shared)

# Phase Page Produces
1 Lex Lexer Tok[] — flat token stream with 1-indexed positions
2 Parse Parser Program — items + a flat Expr[] node slice
3 Check Type checker Checked — resolved types, effect rows, node stamps
4 Analyze Analysis builtin surface tables, op discovery, builtin refs

The frontend is strictly layered: each phase consumes the previous phase's output and nothing else. The analysis layer depends only on parser types, so both backends consume it without pulling in the evaluator.

Backend: the interpreter

Interpreter (CPS) →

Before either backend consumes the CPS IR, toCps's final stage — optimizeCps (cps_opt.ts, with cross-function inlining in cps_inline.ts) — runs the optimizer: single-use closures and small non-recursive bodies are inlined at their call sites, then four local rewrites (read-temp substitution, prim-let fusion, exit-continuation beta, dead binding drop) iterate to a fixpoint. Every rewrite preserves the CPS shape and the run-trace contract, so both backends stay oblivious to the optimizer.

newCtx(interp?) seeds state; the caller checks the program (checkProgram(prog, ctx.checked)), then exec(prog, ctx, checked) fails fast on statically-unhandled non-builtin ops (frontend/pipeline.ts's rejectUnhandled — the same gate the wasm pipeline applies before codegen), seeds the referenced builtins into the runtime env, then evaluates under the CPS evaluator (evalE/apply). The one-shot run adds the file-entrypoint gate (pipeline.ts's requireUnitEntry — last expression must be unit); the REPL's runLine skips it. Multi-shot resume is a plain JS closure. Effects with no matching handler reach runTop, which interprets them through the builtin table (or an injected override — tests inject fake fs/time/randomness there).

Backend: WebAssembly

Wasm backend →

prepare runs the frontend (parse → check); compileWithOps consumes the prepared artifacts and runs a five-phase pipeline (discover → optimize → assignIndices → layoutStatics → emit) over plain artifact records, assembles the module (buildModule, including an in-process binaryen shrink pass), and hands the bytes to the host runtime, which instantiates the module and rebuilds JS values across the WasmGC boundary. CPS is compiled explicitly: frames, continuation cells, and resume-as-value. Each phase has its own page under Wasm backend in the sidebar.

The REPL protocol

The REPL and ef run share one pipeline; the REPL just calls it per line with an accumulating context — bindings (both value and type environments) persist across lines.

Details per phase: Parser (closures carry their own node slice, so REPL lines never alias), Type checker (one Unifier carried inside Checked), Interpreter (newCtx/exec semantics).
