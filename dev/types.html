Type checker

checkProgram(prog, acc?): Checked — Hindley-Milner-flavoured inference with effect tracking: every function type carries an effect row, and effects performed without a matching handler surface in the program's residual row.

Inputs and outputs
in Program (items + flat node slice from the Parser)
in acc — the previous Checked, passed back to accumulate bindings (the REPL protocol)
out Checked — bindings, resolved types, effect rows, per-node stamps

The Unifier

One instance per checking session; all mutable unification state lives in it, carried inside Checked across REPL lines. Type values themselves are plain data — and so is the unifier: free functions over it (uniRes, uniUnify, …) thread the state explicitly, so independent checkProgram calls (in tests!) never share state.

Effect rows deserve a second look: a row is a concrete set of performed ops — op names plus possibly unbound EffVar members — or a bare unbound EffVar. This makes higher-order builtins effect-polymorphic — map : ((a) -> b ! e, [a]) -> [b] ! e with a fresh e per instantiation: map(pureFn, xs) performs nothing, map(fn(x) { Out!(x); x }, xs) performs exactly { Out }. The variables also propagate through user code: calling an unannotated parameter forces it into a function type with a fresh row variable, and that variable joins the enclosing function's row — so a polymorphic caller (apply, a handler-delivered closure) stays effect-tracked, and a closure whose row names an op cannot slip past the residual-row gate by escaping its handler. A row variable that never unifies with anything concrete (a polymorphic value passed around but never applied to an effectful callee) contributes nothing — no constraint ever tied it to a perform. Recursion makes a row variable self-referential (ρ = {ρ}): semantic consumers collapse that circle to its non-cyclic contents (∅ for pure recursion), while display keeps the variable — a never-constrained parameter's row shows as a generic row on the argument type.

Checking a program

  1. Register effect items (unannotated params become fresh variables) and type aliases.
  2. Infer each expression item; residual per-item effect rows land in Checked.unhandled (ops-minus-handled matching is done here — the checker can see through calls, which is exactly what a syntactic AST walk cannot).
  3. Num-type resolution + width-stamp post-pass after all items: resolveNums propagates op-linked num-type widths to a fixpoint. Untyped num types stay valid through checking — the REPL acc keeps them (per-read copies flex per use), while backends lower them to the defaults (int → i64, float → f64) via widthOf at every stamp site. Divergent reads (one untyped binding read at several widths) are marked adaptFrom so the backends adapt the stored box's representation; stamps are then written from the resolved types (nodeTypes, stamps.numKind, …).

Load-bearing rules

Rule Consequence
Strict widths i32 + i64 is a type error; @as(expr, T) is the one conversion (float→int truncates, bool→0/1)
Num-type literals 1 flexes to any numeric width, 1.5 to any float width — each read flexes its own copy of the num type; backends lower unresolved num types to i64/f64 via widthOf, never widened at parse time; the REPL alone echoes them as untyped num types (42 : int, x := 42; x → 42 : int, PI : float)
f32 stamping every producing node is stamped; interp frounds, wasm emits a demote/promote round-trip — f32 precision holds end to end
any is absorbing escape hatch; inferred-any bindings warn (explicit annotation silences)
Op! needs a declaration Op :: effect(args): ret — ret is what Op!(…) evaluates to, i.e. what resume injects
Effectful bodies need ! { … } a ::/fn whose body performs effects must declare a superset; pure bodies may omit it; the declaration pins unannotated parameters' effect variables to the declared set (empty declaration + performing parameter → rejected)
No-Return handle rule body effectful → result type is not unified with the body type (handlers transform results); body pure → R ~ bodyType
resume k type k : (effectRet) -> R where R is the handle result type, not the body type
Value restriction only lambda RHS are generalized; literals and bracket literals stay monomorphic — keeps mutation sound
Width ambiguity a generalized lambda doing numeric ops on an unannotated parameter is rejected: the width would flex per call site while the body fixed one
