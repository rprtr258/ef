Interpreter (CPS)

The CPS evaluator plus the execution pipeline shared by ef run and the REPL.

Why CPS

The continuation is a plain JS function, so resume is genuinely multi-shot: the handler may call k zero, one, or many times, and each call re-runs the rest of the computation. Generators can't do this — they are single-use; CPS makes nondeterminism (Choose-style search, backtracking) a plain loop over k.

Because everything is tail-call structured, JSC's TCO keeps the JS stack O(1) for tail calls; non-tail recursion allocates heap frames instead of stack frames (slow, but no stack overflow).

The conversion is selective: a function whose resolved effect row is empty and whose body has no suspending call in its tail chain converts direct-style — its boundary delivers with dret instead of jumping $ret, and calls to classified-pure callees are dcalls that bind results in-frame. A mixed function — empty row with internal handlers — keeps the direct boundary: its handler islands run over the ambient chain like any CPS region, and the tail handler's continuation resolves to the caller's continuation at runtime.

Core shapes

Shape Meaning
Value null · number · bigint · string · boolean · Value[] · Closure · Native
Closure {params, fun, ir, env, typ?} — fun indexes the closure's own CPS IR function table, so closures stay valid across REPL lines and programs
Native {fn: (args, k) => Outcome} — CPS builtins
Cont (Value) => Outcome
Outcome {tag: "done", value} or {tag: "eff", op, args, k} — a trapped effect

evalTerm(t, ir, env, k) dispatches over the CPS IR term; apply(f, args, k) dispatches native vs closure (a dcall whose callee is a direct closure applies it inline at the site instead).

Width normalization

The checker stamps every numeric node with its width (numKind); the CPS IR carries those stamps as norm marks on the bind sites (prim results, binds, continuation parameters, dcall results). normWidth normalizes the produced value exactly like the wasm backend's per-width ops:

Stamp Normalization
u8 v \& 255 (BigInt input: Number(BigInt.asUintN(8, v)) \& 255)
i32 v | 0 (BigInt input: Number(BigInt.asIntN(32, v)))
u32 v >>> 0 / asUintN
f32 Math.fround(v)
f64 plain number
i64 / u64 BigInt.asIntN/asUintN(64, …) — exact beyond 2^53

Unstamped nodes (polymorphic uses) pass values through; operators then dispatch on the runtime representation. widthOp itself never converts between widths: the checker resolves literal widths per site, so a stamped operator's operands arrive already in its representation (divergent reads — one untyped binding read at several widths — carry adaptFrom and are adapted at the read, not the op).

Effects and handlers

handle(body, cases, env, k) evaluates the body with a terminal continuation; every Outcome it produces flows into run(out, kOuter):

  • done → the Return case binds the value (and a resume that just re-returns it) and evaluates the case body under kOuter; with no Return case, the value passes to kOuter unchanged.
  • eff with a matching case → the case body runs with the effect's params bound and resume bound to run(out.k(args[0]), k2) — the captured continuation is the resume. Because out.k is a plain closure, calling it repeatedly is multi-shot resume.
  • eff with no matching case → the outcome is re-thrown outward with a wrapped continuation: k: (v) => run(out.k(v), kOuter). When an outer handler eventually resumes, the wrap re-enters this frame's chain — deep handlers, with lookup resolved outward at bubble time.

Case bodies run outside their handler (under kOuter), so an effect performed inside a case body propagates to the next enclosing handler.

runTop and interpretation

runTop(out, interp?, trace?) loops over a trapped outcome: an interp override is checked first (tests inject fake fs/time/randomness there), then builtinInterps (the builtin table's default interpretations — real I/O), else throw new Error("Unhandled effect: …"). Every host call — override or default — goes through trace.ts's runTraced, which appends one event ({op, args, result}) to the run trace when trace is given (trace.ts, the run-trace leaf module): the capability log the parity harness compares between backends.

The exec pipeline

newCtx(interp?) → fresh pipeline state; exec(prog, ctx, checked) — the program is checked by the caller before the interpreter runs (run checks once after parsing; a REPL line checks against ctx.checked):

  1. Fail fast on statically unhandled ops (rejectUnhandled in frontend/pipeline.ts — the one gate both backends call right after prepare; the wasm pipeline applies it before any codegen): any op in checked.unhandled that is neither a builtin effect nor covered by ctx.interp throws before evaluation begins — a program that would die mid-run after side effects dies before its first side effect. ctx.checked is assigned only after the check passes, so a rejected REPL line leaves the accumulator untouched (like a type error does).
  2. seedBuiltins(ctx.env, builtinRefs(prog)) — bind exactly the builtins this program references (the checker's no-shadowing rule keeps user bindings off builtin names, so seeding never overwrites anything).
  3. Evaluate each item: runTop(evalE(item, …)). Returns {value, lastType, lastIsExpr} — lastIsExpr implements the REPL echo rule (declarations print nothing).

run(src, interp?, args?, trace?) = one-shot parse → entrypoint gate → exec: run is the file-entrypoint seam, so requireUnitEntry (frontend/pipeline.ts, next to rejectUnhandled) throws before evaluation unless the program ends in a bare unit-typed expression — the CLI prints no result for the same reason. The REPL calls newCtx once and exec per line (through runLine, which skips the gate — echoing per-line values is the REPL's protocol), so bindings accumulate.

The evaluator and the builtin table reference each other only at runtime (apply is called from builtin closures; unhandled effects read the table's default interpretations) — safe from any entry point because the defaults are derived together with the table itself.
